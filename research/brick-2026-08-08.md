# Postmortem: the stock-over-stock OTA that bricked GLASSES-12C3EF

**Status: RESOLVED. The unit was repaired on 2026-08-20 and works.** `GLASSES-12C3EF`
advertises, connects and answers as stock, after a healthy pair's application region was
written onto it over SWD. `research/aprom-write-2026-08-20.md` is that run.
**Scope:** what was done, the exact mechanism from the disassembly, and the repair.
**Verdict: the cause was the image, not the config, and replacing the image fixed it.**

*Corrected 2026-08-20: this header read "unit unresponsive since 2026-08-08" and the
verdict below built up through four wrong theories before reaching the right one. Both are
kept, because the wrong turns are the expensive part and this document's own history is
the best argument for the confidence markers. But a cold reader must not come away
thinking the unit is still dead.*

**The chain, settled:**

| Step | What | Confidence |
| --- | --- | --- |
| the commit | OTA ctrl `03` handed to the bootloader, which **worked perfectly** and faithfully installed the wrong application | *verified*, track 48 |
| the wrong application | the vendor APK's image is 7,532 bytes smaller than what these units run and its registrar fills **22 of 26** callback slots | *verified*, track 47 and `image-silicon-match.md` |
| the fault | the app tail-calls through an uninitialised RAM pointer at `0x20000074`, the `bx` at `abs 0x10f54`, and hardfaults at `pc 0x00000d38` | *verified*, caught halted in `Handler HardFault` |
| not the cause | `CONFIG0`. `0xFFFFFFBF` is what the bootloader writes on purpose. The config repair ran first and did nothing | *verified* |
| the fix | write a working unit's application region over SWD, 150 pages, `0x16800`-`0x293ff` | *verified* 2026-08-20, it came back |

**Why the repair is also the proof of the diagnosis.** `ota.check`'s device-match read the
donor image against unit 1's own BLE stack **before** anything was written and reported
"all 23 dispatched callback slots are registered". An application that registers them does
not fault where the APK's 22-slot registrar did. The prediction was offline; the unit
advertising is the confirmation.

**Five claims in this document were wrong and are corrected in place**, and a sixth is
above: the value in `CONFIG0`, the blank LDROM, the instruction to erase the config page
and leave it erased, the "bit 6 took, bit 7 did not" reading of `CONFIG0`, the premise
that restoring `CONFIG0` would revive the unit, and the status line saying it never did.
**Read "What SWD actually found", "Why the value is `0xFFFFFFBF`" and "The config repair,
and why it did not work" before acting on any section below them.**

### Why the value is `0xFFFFFFBF`

**`0xFFFFFFBF` is the bootloader's own deliberate value, not a failed write.** *derived*
from track 48's read of the LDROM, `research/ldrom-2026-08-19.md`. The bootloader's last
act, at `ld 0x100b86`, reads all four config words, overwrites `CONFIG0` with `~0x40 =
0xFFFFFFBF`, erases and reprograms the page, then `SYSRESETREQ`. It is a run-once,
hand-back-to-APROM step. So the device correctly held the value its own bootloader writes,
and `CBS = 10` selects boot-from-APROM, which is right and always was after an update.

*Corrected 2026-08-19: this section previously read "bit 6 took, bit 7 did not", inferring
a partial write and guessing that `CBS` was a single implemented bit. That was wrong and it
was written before the bootloader had been read. There was no partial write and nothing was
refused. The application's own commit path at `abs 0x1ca4c` builds `0xFFFFFF3F`, but the
bootloader runs after it and overwrites `CONFIG0` with `0xFFFFFFBF`, so the bootloader's
value is what survives. Both bits are implemented and writable.*

**What this changes about the repair.** The config page was very likely never wrong. See
"The config repair, and why it did not work": the repair did not restore a factory value,
it changed the bootloader's intentional `0xFFFFFFBF` to the erased `0xFFFFFFFF`, and nobody
has ever read `CONFIG0` on a working unit to know which is correct.

**The causal story is now settled and it is not `CONFIG0` at all.** *derived* from track
48. The fault is a tail call through an uninitialised RAM function pointer, unrelated to any
config bit; the detail is in "The config repair, and why it did not work" below.

## The config repair, and why it did not work

*verified* on the bricked unit, 2026-08-19, over the same probe. This section outranks the
recovery plan and the odds below it, both of which were written before the repair ran.

`research/tools/fmc-repair-config.sh --yes` ran and completed, config-write-enable only so
APROM and LDROM were hardware-locked throughout. It erased the config page and reprogrammed
the three words the vendor writer keeps, leaving `CONFIG0` erased:

| Word | Before | After | |
| --- | --- | --- | --- |
| `CONFIG0` | `0xffffffbf` | **`0xffffffff`** | erased, the intended change |
| `CONFIG1` | `0x00000000` | `0x00000000` | rewritten unchanged |
| `CONFIG2` | `0x00000000` | `0x00000000` | rewritten unchanged |
| `CONFIG3` | `0x0003dbff` | `0x0003dbff` | rewritten unchanged |

The erase read back `0xffffffff` on all four words mid-sequence, the FMC fail flag stayed
clear, and the result verified on read-back. **The write is correct and it persisted across
a power cycle**, read back as above after the unit was powered fully off and on (twice, by
hand). Nothing else on the device was touched.

**This did not "restore a factory value", and that framing was wrong.** *Corrected
2026-08-19 after track 48 read the bootloader.* `0xFFFFFFBF` is the value the bootloader
deliberately writes to `CONFIG0` as its handoff step (see "Why the value is `0xFFFFFFBF`").
The repair changed that intentional value to the erased `0xFFFFFFFF`. Both appear to select
boot-from-APROM, so it very likely did no harm and the unit's behaviour is unchanged either
way, which is consistent. But **nobody has ever read `CONFIG0` on a working unit**, so it is
entirely possible `0xFFFFFFBF` was the normal value and the config page was never wrong. A
single `mdw 0x00300000` on a healthy pair would settle it cheaply; it is in "Next steps".

**It did not revive the unit.** After a genuine power-on reset the CPU boots APROM and
hardfaults at the identical site as before the repair:

| Read | Before repair | After repair + POR |
| --- | --- | --- |
| mode | Handler HardFault | Handler HardFault |
| `pc` | `0x00000d38` | `0x00000d38` |
| `msp` | `0x200025a8` | `0x200025a8` |
| stacked `pc` / `lr` | not read | `0x6e5cb82a` / `0x00010e55` |

**So `CONFIG0` was not the fault**, which the found cause below now confirms outright. This
closes the "restore the byte-state and it comes back" argument the recovery plan and the
odds section rest on. The device is not damaged and not lost: the CPU boots, the part is
unlocked, and the dumps are intact.

**The fault is a tail call through an uninitialised RAM function pointer.** *derived* from
track 48, `research/ldrom-2026-08-19.md`, and it matches the recorded frame exactly:

    abs 0x10f54:  ldr r0,=0x20000014 ; ldr r0,[r0,#0x60] ; bx r0

`bx r0` branches to whatever was just loaded from `[0x20000014 + 0x60] = 0x20000074`, which
held `0x6e5cb82a`, so `r0` and the stacked `pc` are equal, and the stacked `lr` is
`0x10e55` because `abs 0x10e50` is `bl 0x10f54` and `bx` leaves `lr` alone. The
struct-filling function at `abs 0x10e24` writes offsets `0x00/0x04/0x14/0x1c/0x20/0x24/
0x28/0x2c` and **not** `0x60`, so the slot at `0x20000074` is used before it is filled: the
fault is **registration order, in RAM, not flash content**.

**This vindicates the caveat on the working-unit diff, and it matters for method.**
`0x6e5cb82a` appears nowhere in the 256 KB dump at any alignment, so it is a RAM value. A
flash-only byte diff of a healthy unit against unit 1 would **not** have found this fault.
The diff is still worth doing for the `CONFIG0` question and to eliminate flash candidates,
but it was never going to explain the crash. Disassembly did.

**You can read the fault frame with no probe at all.** *derived* from track 48. `abs 0xd3c`
holds the string "In Hard Fault Handler", and the application prints all eight stacked
registers over UART before spinning. A serial adaptor on the UART and a power cycle give the
whole frame, no SWD needed. Worth reaching for before clipping a probe onto anything.

**Do not erase `0x3d800` on a hunch.** Nothing establishes it holds only OTA state, and a
half-erased staging pointer could make a booting device copy garbage over the application.
With the cause now known to be RAM registration order, that page is unlikely to be the fix
anyway.

### The fault is intermittent, not every-boot

*verified* on live silicon, 2026-08-19, read-only. Later the same day the unit was caught
**halted in Thread mode, running its application**, `pc` advancing across six samples
(`0x1fcc0`, `0x109d8`/`cc`/`ca`, `0x1fcbe`, `0x140c8`), `msp` near the top of stack, no
active exception. It had self-recovered from the hardfault with no intervention (only the
config repair and power cycles preceded it; the likeliest path is the fault handler
resetting and a later boot winning the race). **So the hardfault is intermittent**, which is
the signature of a registration/init race on the callback slot.

The RAM confirms it. On this good boot the faulting slot `0x20000074` held **`0x00020805`, a
valid code pointer**, not the `0x6e5cb82a` of the faulted boot, and the struct at
`0x20000014` was populated with **dense sequential code pointers up to `+0x68`**, which reads
as a table copied wholesale rather than 27 setters run one by one. Capture:
`firmware/sram-unit1-2026-08-19.bin`.

**But the radio never comes up, and that is arguably the more diagnostic fact.** *verified*
2026-08-19 by track 48: two 20-second passive BLE scans while unit 1 was in this good boot
found only `GLASSES-125B37` and `GLASSES-12E69E`, never `GLASSES-12C3EF`. So even on a boot
where the CPU runs its application in Thread mode, the BLE stack does not advertise. The
application executing and the radio failing to initialise are separate facts; a good boot is
not a working unit.

**This is a genuine tension with the static analysis and is left for track 47 to
reconcile.** Track 47 reports that nothing in the 256 KB writes `0x20000074` (no `str` with
a tracked base, no caller of the `+0x60` setter). Yet on a good boot the word holds a valid
pointer and the application runs through the `bx r0`. Something writes it. The most likely
reconciliation is a store through a base the static scan could not track (an indirect write),
so "nothing writes it" is really "no statically-tracked store writes it". Track 47's file is
`research/hardfault-0xd38-2026-08-19.md`; do not edit it from here.

**The Cortex-M0 gives no fault classification.** Reading `CFSR`/`HFSR`/`DFSR`/`MMFAR`/`BFAR`
at `0xE000ED28` and `VTOR` at `0xE000ED08` returned all zero, because ARMv6-M does not
implement them. The only route to a fault type on this core is the UART print (track 48).

## Next steps, ordered

The crash mechanism is found; what is not yet known is why unit 1 reaches it and a working
unit does not. Cheapest and safest first.

1. **Done: the fault site is disassembled.** Track 48 found the tail call through the RAM
   pointer at `0x20000074` (see "The config repair, and why it did not work"). The remaining
   question is the **trigger**: the application code is byte-identical to stock, so some
   input or persistent state steers this unit into the unfilled-slot path. That is offline
   work on the dump, owned by tracks 47 and 48; do not duplicate it.
2. **Read `CONFIG0` on a healthy pair.** *Cheap, high value, and Jacob's call to clip onto
   working hardware.* A single `mdw 0x00300000` settles whether `0xFFFFFFBF` is the normal
   value, which decides whether the repair changed `CONFIG0` away from the correct one and
   whether it needs putting back. Track 48 lists this as one of three prerequisites before
   `--ldrom-verified` could ever be honestly passed. One word, no full dump.
3. **Diff a healthy unit against unit 1.** *Needs Jacob's explicit agreement before the
   probe touches working hardware.* A read-only 256 KB dump of an idle, never-OTA'd pair,
   then `dumpcheck compare` or a byte diff against `dump-unit1-2026-08-19-a.bin`, shows which
   flash bytes differ and could reveal the flash trigger for the different code path. **It
   will not show the crash itself**: `0x6e5cb82a` is a RAM value absent from all 256 KB, so
   a flash diff cannot explain the fault, only a flash-borne trigger for it. Dumping a
   healthy unit needs a `RST` line the dead one did not (`research/hardware-access.md`,
   "Dumping a healthy unit is harder"). Do not use unit 2 (`GLASSES-125B37`) while it is
   driven over BLE.
4. **Read the fault frame over UART, no probe.** `abs 0xd3c` "In Hard Fault Handler"; the
   app prints all eight stacked registers before spinning. A serial adaptor and a power cycle
   give the frame with no SWD. It is debug UART0 TX on P1.3 (QFN32 pin 11), 115200 8N1, not
   the panel UART; possibly the unlabelled `K` pad in the `V+ G K VD` group, worth a
   continuity check. Detail: `research/ldrom-2026-08-19.md`, "The debug console".
5. **Do not erase `0x3d800` blind.** With the cause now known to be RAM registration order,
   that page is unlikely to be the fix, and erasing it has its own risk (see the warning
   above).

## The mechanism, exactly

*verified* from bytes at `abs 0x1c9c8`-`0x1ca68` and `abs 0x17a78`-`0x17b00`.

After the CRC matches and the info record is written, `abs 0x1c9c8` runs:

| Site | Instruction | Effect |
| --- | --- | --- |
| `0x1ca26` | `ldr r1, [r1, #0xc]` | reads `record[0xc]` from `0x20002d70` |
| `0x1ca28` | `cmp` against `0xdbd2`, then `0xdbc3` | proceeds only for a known section flag. Ours was `0xdbc3` |
| `0x1ca44` | `movs r1,#4` / `bl 0x179d8` | reads **four** config words into a stack buffer |
| `0x1ca4c` | `movs r0,#0xc0` / `mvns r0,r0` | builds `0xFFFFFF3F` |
| `0x1ca50` | `str r0, [sp]` | overwrites only `CONFIG0` in that buffer |
| `0x1ca56` | `bl 0x17a78` | erase-and-reprogram the config page |
| `0x1ca62` | `str r0, [r1,#0xc]`, `r0=0x05FA0004`, `r1=0xE000ED00` | `AIRCR` `SYSRESETREQ` |
| `0x1ca68` | `b .` | spin until the reset lands |

The config writer at `abs 0x17a78` is a read-modify-write of the whole config page:

- `lsls r5, r2, #6` with `r2 = 0x5000C000` produces `0x00300000` by 32-bit overflow.
  That is the config aperture, built arithmetically, which is why a literal search for
  `0x300000` finds nothing. Same trap `fwtool.ts` warns about.
- `ISPCMD 0x22` page-erase at `0x00300000`, then `ISPCMD 0x21` programs `CONFIG0`,
  `CONFIG1` (`0x300004`), `CONFIG2` (`0x300008`), `CONFIG3` (`0x30000c`).
- Only `CONFIG0` differs from what was read back. The other three are rewritten
  unchanged.

**So the entire persistent change to the config page is the value written to `CONFIG0`.**

*Corrected 2026-08-19: this said "the entire persistent change is `CONFIG0 = 0xFFFFFF3F`",
on two counts. The device holds **`0xFFFFFFBF`**, not `0xFFFFFF3F`, so bit 7 never took;
and the commit also left an info record at `0x3d800`, so the config page is not the only
persistent change. Both are in "What SWD actually found". The disassembly above is
unaffected and still reads correctly.*

`~0xC0` clears bits 7 and 6. On this Nuvoton-derived FMC those are `CBS`, the chip boot
select, and `CBS = 00` would mean **boot from LDROM**. Every other bit is left at the
erased default of 1, including bit 1, which on NuMicro is `LOCK` and where **0 means
locked**. *derived*: the bit positions are Nuvoton's, applied to a Panchip part. What is
*verified* is the value the code builds and that the firmware changes nothing else in
that page. **What the silicon shows is that only bit 6 is writable**, so the two-bit
`CBS[7:6]` reading does not hold on this part.

## Why it did not come back: the LDROM question

**Closed 2026-08-19, and the answer was no.** This whole section was the leading
hypothesis and it is now *disproven* on two independent readings: the LDROM aperture at
`0x00100000` holds a valid image rather than blank flash, and the halted CPU's stack
pointer belongs to APROM's vector table, not LDROM's. See "What SWD actually found".

The section is kept rather than deleted because the reasoning below is still the correct
account of *why the two addresses had to be checked*, and because WRITING.md requires a
wrong entry to be corrected in place so the next session does not re-derive it.

**Superseded hypothesis: `CBS = 00` points the CPU at an LDROM aperture that has nothing
in it.** *disproven*.

The confusion this rests on, and it is a real one:

- Nuvoton parts map LDROM to a **separate aperture, `0x00100000`**, not into the main
  `0x0`-`0x3ffff` array.
- Panchip's `section_cfg.h`, which `packages/core/src/ota.ts` mirrors, defines
  `FLASH_BOOTLOADER_ADDR = 0x0003dc00`, which is inside APROM.

Those are two different places. If `CBS = 00` boots `0x00100000` while the vendor's
"bootloader" lives at `0x3dc00`, then setting `CBS = 00` sends the CPU somewhere that
may never have been programmed. Blank flash reads `0xFFFFFFFF`, so the CPU loads
`SP = 0xFFFFFFFF` and `PC = 0xFFFFFFFF` and faults immediately at reset. That is
exactly the observed behaviour: powered, charging, no radio, no LEDs, no button
response.

**They are the same place.** *verified* 2026-08-19: a 9216-byte read at `0x00100000` is
byte-identical to `0x0003dc00` in the main dump, so the aperture is an alias of the
region `section_cfg.h` calls the bootloader. There was never a second, unprogrammed
LDROM. It follows that **every 256 KB dump already contains the bootloader**, which is
the reading the `--ldrom-verified` gate was waiting for.

The observed behaviour is also explained differently: the CPU is not loading
`0xFFFFFFFF`, it is running APROM and hardfaulting at `pc 0x00000d38` with 160 bytes of
APROM stack used. Powered, charging, no radio and no LEDs look identical from outside
whichever of the two is happening, which is exactly why this needed a read rather than an
argument.

**This document has always listed the bootloader as unverified and it was never
checked.** `firmware-flashing.md` says so plainly under "Still unverified": *"Whether
the bootloader validates the staged image before copying, and what it does when the
record is absent"*. Committing an OTA depended entirely on that unverified component.

### The corroborating evidence, which was visible in advance

| Signal | Reading at the time | Better reading |
| --- | --- | --- |
| ctrl `01` replied `app=0 dev=0 pro=0` | "suspicious", noted and passed over | the unit's own OTA version struct at `0x20002f80` is zeros. A subsystem never exercised in production looks like this |
| the vendor app refuses an OTA when version major >= 10; ours reports 10 | "the vendor app is not a recovery route for us" | **the vendor deliberately does not OTA these units.** Equally well supported by the same fact, and never considered |

Neither is proof. Together they suggest the OTA commit path on `TR1906R04-10` was
shipped and never used, which is consistent with a missing LDROM image.

## Why the unit is probably still alive

Every row below was *derived* when written and all but one is now *verified* on the
device. Upgraded 2026-08-19.

| Claim | Confidence |
| --- | --- |
| The application at `0x16800` was never erased | ***verified* on the device**. `dumpcheck` matches the vendor OTA plaintext byte for byte, across all 150 pages |
| The staged copy at `0x29400` is intact and CRC-correct | ***verified* on the device**. It reads as a plaintext copy of the stock container |
| The part is not read-locked | ***verified* on the device**. 256 KB read back as real content, not `0xFFFFFFFF` |
| The fault is one word in the config page | **disproven 2026-08-19**. The config word was never wrong (it is the bootloader's own value) and it is not the fault; the fault is a RAM registration-order tail call. See "Why the value is `0xFFFFFFBF`" and "The config repair" |
| Restoring it needs only a page erase, not a computed write | **wrong, corrected below** |

**The last row is wrong and it matters.** *Corrected 2026-08-19: this said "the fix is to
erase the config page and leave it erased. No value has to be calculated or invented."
The config page is **not** otherwise blank. It holds `CONFIG1 = 0x00000000`,
`CONFIG2 = 0x00000000` and `CONFIG3 = 0x0003dbff`, all of which an erase destroys. Note
that `0x0003dbff` is the last byte before the LDROM alias at `0x3dc00`, so it is unlikely
to be meaningless.*

**The fix is erase, then reprogram `CONFIG1`, `CONFIG2` and `CONFIG3` with the values
already read, leaving `CONFIG0` at its erased `0xFFFFFFFF`.** That is a read-modify-write
of the whole page, which is exactly what the vendor's own writer at `abs 0x17a78` does,
so the sequence is *verified* from shipped code rather than invented. Setting bit 6 back
to 1 cannot be done without an erase, because programming only drives bits to 0.

**The one genuine reassurance about erasing this page:** an erase can only drive bits
towards 1, and `0xFFFFFFFF` is the unlocked, factory-default `CONFIG0`. So an erase
interrupted by a brown-out cannot set the `LOCK` bit and cannot lock the part. The
catastrophic risk in this repair is not the erase, it is issuing the wrong `ISPCMD`:
`0x23` is chip erase (*corrected 2026-08-20: this said `0x26`, which is not a command at all; vendor `fmc.h` gives `FMC_ISPCMD_CPERASE` = `0x23`*).

**Steps 0 to 3 are done, 2026-08-19, and all three passed.** The dumps are
`firmware/dump-unit1-2026-08-19-{a,b,c}.bin` (identical) and
`firmware/ldrom-unit1-2026-08-19.bin`, gitignored, with a copy outside the repo. Step 4
is rewritten below; steps 5 and 6 stand.

0. **Done.** The case is open and the header is confirmed on our own board. Location,
   pitch, silkscreen, the wiring map and the one misalignment that damages the board are
   in `hardware-access.md`, "The debug header: 2.54 mm, five through-holes, LED side".
   The practical fact for this repair: **no soldering needed**, a 6-pin 2.54 mm pogo
   probe clip fits, and the Debug Probe's JST-SH-to-male-jumper lead plugs into it.
   *Corrected: this step gave the pad order as `RST CLK DAT G VD`, which came from a
   low-resolution FCC image. The board in hand is silkscreened `RST EK ED G VD`.*
1. **Attach SWD** to `RST`, `EK`, `ED`, `G`. Leave `VD` unconnected and run the glasses
   from their own battery. **Done.** Orange to `EK`, yellow to `ED`, black to `G` on a
   Raspberry Pi Debug Probe worked first try; the colours are in `hardware-access.md`.
2. **Read `0x16800`.** If it matches the decoded stock image, the application is intact
   and this is purely a boot-select fault. If it reads all-`FF` or garbage, the
   bootloader ran and half-wrote APROM, which is still fixable but needs a full
   reflash. **Done: it matches byte for byte.** The application is intact.
3. **Read `0x00100000` and `0x0003dc00`.** This settles the LDROM hypothesis outright:
   whichever of the two is blank tells us where the boot went. Record both; nobody has
   ever dumped either on this family. **Done: neither is blank and they are aliases.**
4. **Erase the config page at `0x00300000`, then reprogram `CONFIG1`, `CONFIG2` and
   `CONFIG3` to `0x00000000`, `0x00000000`, `0x0003dbff`.** Read back and require
   `CONFIG0 = 0xFFFFFFFF` with the other three restored. *Corrected 2026-08-19: this step
   said "erase the config page and read back `0xFFFFFFFF`", which would destroy three
   programmed words. See "Why the unit is probably still alive".* **Superseded by outcome:
   this ran, and `0xFFFFFFFF` is now doubted to be the right `CONFIG0` at all, since
   `0xFFFFFFBF` is the value the bootloader deliberately writes. See "The config repair".**
   **Do the validation ladder in `hardware-access.md` first.** Its step 1, reading a
   known address back through the FMC and comparing with `mdw`, confirms the FMC base,
   the `0x59/0x16/0x88` unlock keys, the `ISPCON` bits and the trigger protocol **without
   a single write**. Then erase the already-blank info backup page at `0x3da00` as a
   no-cost live erase before touching config.
5. **Reset and see if it advertises.** If APROM was intact, that should be the whole
   repair. If it is still dead, the next suspect is the info record at `0x3d800`, not the
   application. **Done 2026-08-19, and it is still dead.** Step 4 ran, the config page is
   restored and verified persistent across a power cycle, and the unit still hardfaults
   identically. See "The config repair, and why it did not work". The next suspect is
   indeed `0x3d800`, but read the disassembly first.
6. If APROM was damaged, program `0x16800` from the decoded stock image. We have the
   exact bytes: `bun research/ota-codec.ts decode firmware/TR1906R04-10_OTA.bin`.

The register sequence does not have to be guessed, because the firmware's own is
*verified*: unlock `SYS_WRPROT` at `0x50000100` with `0x59, 0x16, 0x88`; FMC at
`0x5000c000` with `ISPCON +0`, `ISPADR +4`, `ISPDAT +8`, `ISPCMD +0xc`, `ISPTRG +0x10`;
`ISPCMD` `0x00` read, `0x21` program, `0x22` page erase; poll `ISPTRG` bit 0; failure is
`ISPCON` bit 6. Config writes additionally need `CFGUEN`, `ISPCON` bit 4.

**`hardware-access.md` warns to delete `ISPCON_CFGUEN` from OpenOCD's
`numicro_init_isp()` before building. That advice is for firmware work. This repair is
the one case that genuinely needs `CFGUEN`, because the config page is the thing being
fixed. Set it deliberately, for this one operation, and not by leaving it on.**

## Odds, honestly

**Outcome, 2026-08-19: the config repair was run and failed to revive the unit, and the
real cause has since been found by disassembly.** The estimates below were written before
either happened and are kept as the record of the reasoning. The lesson they anticipated
held: the argument rested on "restore the exact byte-state of a working unit", and that was
never a restore (the changed value was the bootloader's deliberate one, not a known-good
one) and would not have mattered anyway, because the fault is a RAM registration-order tail
call, not a config bit. The part is still recoverable in principle; the odds now hang on
finding why unit 1 alone reaches the faulting path, not on any byte-restore.

**Revised 2026-08-19, after the device was read.** Better than before on every count that
can be measured, and worse on one that cannot.

What used to be inference is now *verified*: the part is unlocked, the debug port works
reliably enough for three byte-identical 256 KB dumps, the application is byte-identical
to stock, and `CONFIG0` differs from the factory value by exactly one bit. We also now
hold a full dump, so a mistake that was unrecoverable on 2026-08-08 is merely expensive
today. **Nobody has to guess what a working unit's flash looks like any more.**

The one thing that got worse: **the causal chain is no longer understood.** The old story,
`CBS` pointing at blank LDROM, is disproven, and no replacement explains how one config
bit makes an unmodified application hardfault. So the repair rests on "restore the exact
byte-state of a working unit" rather than "fix the identified fault". That is a weaker
argument, though still a good one.

Against it: nobody has *written* to a part in this family, the `0x59/0x16/0x88` unlock
keys are *derived* from the vendor's own code but never driven from outside, and the part
ID at `0x50000000` reads `0x00000000`, so OpenOCD's `numicro` driver cannot probe it and
the TCL-poke route is the only one left.

The scenarios that would make it genuinely unrecoverable are the ones we now have
*verified* evidence against: a locked part and a dead debug port. What remains is a
device that stays dead after a correct repair, which costs the unit but nothing else.

## SWD is not just the repair, it is the better flashing route

Worth stating plainly, because "the flashing step failed" invites the wrong conclusion
that firmware work is now blocked. It is the opposite.

The commit path that failed is `stage to 0x29400` -> CRC -> info record -> `CBS = 00`
-> reset -> **unverified bootloader** -> copy to `0x16800`. **SWD writes `0x16800`
directly.** No staging bank, no handshake, no info record, no `CONFIG0` change, no
bootloader. The component that bricked the unit is absent from the path.

It also dissolves the constraint that shaped every design decision so far.
`PROTECTED_REGIONS` in `ota.ts` exists because OTA recovery needs the running
application to bring up BLE and expose `fd00`, so patching the GATT table, the OTA
handler, the flash driver or the descrambler is self-sealing. Over SWD, recovery does
not depend on the application at all.

| Constraint under OTA | Under SWD |
| --- | --- |
| Protected regions are untouchable | all editable; `ota.check` becomes advisory |
| An image that fails to bring up BLE is a brick | re-flash it |
| ~4 minutes per upload, 18-byte packets, ack-driven | seconds |
| The `fd00` service must be preserved | can be stripped |

`firmware/joggles-v1.bin` needs no change. Write `ota.plaintext()` of it to `0x16800`.
Everything verified about that image holds; it was never implicated.

**The asymmetry that matters:** reading flash over SWD needs no driver, because a read
is a plain AHB-AP memory transaction. Writing needs OpenOCD's `numicro` driver with a
part-ID entry added, or direct FMC register pokes from TCL. The second route is now
much easier than it was, because the exact unlock and ISP sequence is *verified* from
the firmware's own code rather than assumed from Nuvoton's.

## What should have been done

- **Own the recovery route before needing it.** `hardware-access.md` called an SWD dump
  "worthwhile insurance" and it was treated as optional. A £12 probe and a flash dump
  before the first commit would have made this a footnote.
- **Never commit on top of an unverified component.** Staging was verified end to end
  on hardware. The bootloader was not verified at all, and the commit handed control to
  it.
- **Treat an unexplained device reading as a stop condition.** `app=0 dev=0 pro=0` was
  seen, called suspicious, and passed over in the same breath.
- **Read a vendor's refusal as information.** The app declining to OTA these units was
  the manufacturer saying something, and it was interpreted only in terms of what it
  cost us.

## Seeing the cause with your own eyes

The whole diagnosis reduces to four read-only commands. None of them can worsen
anything, and together they either confirm this document or overturn it.

    openocd -f research/tools/pan1020.cfg -c "init; halt; \
      mdw 0x00300000; mdw 0x00100000; mdw 0x0003dc00; mdw 0x16800 8; shutdown"

**Run 2026-08-19. Two of the four predictions were wrong.** Observed values below; the
predictions are kept because the gap between the columns is the whole value of the
exercise.

| Read | Expected if this document is right | **Observed** |
| --- | --- | --- |
| `0x00300000` | `0xFFFFFF3F` | **`0xFFFFFFBF`**. Bit 6 took, bit 7 did not |
| `0x00100000` | `0xFFFFFFFF` | **`0x20000610`**. A valid LDROM image, not blank |
| `0x0003dc00` | unknown | **`0x20000610`**, identical. It is an alias of the aperture |
| `0x16800` | matches `ota.plaintext()` of stock | **matches, byte for byte** |

`0x00300000` reading `0xFFFFFFFF` would have meant the config write never happened. It
did happen, so the disassembly of the write path is sound even though its consequence was
misread.

**A gotcha that cost twenty minutes, and the fix first given for it does not work.**
**Do not read a word with `mdw` from a script. Use `read_memory` and `echo`.**
*verified* 2026-08-19, on unit 1, three times:

    openocd -f research/tools/pan1020.cfg -c '
      init
      halt
      proc rd {a} { return [expr {[lindex [read_memory $a 32 1] 0] & 0xffffffff}] }
      echo "CONFIG0 = [format 0x%08x [rd 0x00300000]]"
      shutdown'

`mdw` results vanish whenever OpenOCD's stdout is not a terminal. Not only behind a pipe
to `grep` or `tail`: they are equally absent when stdout is redirected straight to a
file, and **absent from `-l <logfile>` as well**, which is the case that makes this
expensive, because a log file is exactly where you go looking when a pipe has eaten
something. The values are never written at all rather than written somewhere else.

*Corrected 2026-08-19: this entry said to put `-c "echo {--- marker ---}"` between the
reads and redirect to a file. That is the trap rather than the escape. `echo` output
survives redirection perfectly, so the markers arrive, the values between them do not,
and the result reads as a device that answered nothing.* On the third silent run the
live reading was that the port had dropped or the target had died; it had not, and
`dap info` was answering the whole time. **A read that prints nothing is far more
likely to be this than a dead target**, and the way to tell them apart is `read_memory`
with `echo`, which is what `swdflash`'s generated script already uses for every word
it verifies.

**That invocation is now wrapped by `./research/tools/swd-recon.sh diag`**, which is these
four reads and nothing else. The raw commands stay above because they are the definition
of what the script does:

| Script | Raw equivalent |
| --- | --- |
| `swd-recon.sh probe` | `init; dap info; shutdown`, i.e. is the port alive |
| `swd-recon.sh ids` | `mdw 0xE000ED00`, `mdw 0x50000000`, `mdw 0xE000EDF0` |
| `swd-recon.sh diag` | the four reads above |
| `swd-recon.sh dump <out>` | `dump_image <out> 0x00000000 0x40000` |

`swd-recon.sh` is read-only by construction and no write command may be added to it, so
the config-page erase at step 4 of the recovery plan is not in it and never will be.

## Open questions

- ~~Is the LDROM aperture at `0x00100000` on PAN1020, or is it mapped to `0x3dc00`?~~
  **Closed 2026-08-19: both. They are aliases of one 9216-byte region.**
- ~~Does anything in the vendor's world ever program LDROM, or do these units ship
  without one?~~ **Closed: the unit shipped with one and it is intact.**
- ~~How does one config bit make an unmodified application hardfault?~~ **Closed
  2026-08-19: it does not.** The fault is a tail call through the uninitialised RAM pointer
  at `0x20000074` (track 48), unrelated to any config bit. See "The config repair".
- **Why does unit 1 reach the unfilled-slot path and a working unit does not?** The new
  central question. The code is byte-identical to stock, so a persistent input or state
  steers the registration order. Whether that trigger is in flash (a diff would find it) or
  in RAM (it would not) is open. Tracks 47 and 48.
- **Is `0xFFFFFFBF` the normal value of `CONFIG0` on a working unit?** Nobody has read one.
  If yes, the config page was never wrong and the repair changed a correct value. A single
  `mdw 0x00300000` on a healthy pair settles it. See "Next steps".
- **What are `CONFIG1`, `CONFIG2` and `CONFIG3` for?** `0x00000000`, `0x00000000` and
  `0x0003dbff`. The third is the last address before the LDROM alias, which suggests an
  APROM/LDROM boundary, but nothing confirms it. They must be restored after any config
  erase regardless.
- ~~Is bit 7 of `CONFIG0` implemented at all?~~ **Closed 2026-08-19: yes.** `0xFFFFFFBF`
  with bit 7 set is the value the bootloader deliberately writes (`~0x40`), not a failed
  clear. See "Why the value is `0xFFFFFFBF`".
- Would a `TR1906R04-1-10` unit behave the same? Assume yes until shown otherwise.
