# Postmortem: the stock-over-stock OTA that bricked GLASSES-12C3EF

**Status:** unit unresponsive since 2026-08-08. Cause traced to a single config word;
recovery not yet attempted.
**Scope:** what was done, the exact mechanism from the disassembly, why the device is
probably still alive, and the read-only diagnosis that settles it.
**Verdict: likely recoverable over SWD.** The fault is one word in the config page, the
application was never erased, and the part is almost certainly not locked.

Offsets are `abs` flash addresses.

## What was done

| Step | Result |
| --- | --- |
| `flash info` | connected, replied `80 01`, reported `app=0 dev=0 pro=0` |
| `flash stage joggles-v1.bin --limit 4096` | 228 packets, no commit. **Unit unharmed**, `bun cli probe` normal afterwards |
| `flash commit TR1906R04-10_OTA.bin --yes` | 3672 packets in 221s, device's own CRC matched, replied `80 03 00`, reset itself |
| after | never advertised again. Charges. No response to the button |

The committed image was **the stock container, byte-identical to what the unit was
already running**. No patch, no extension, no key swap. The device verified those exact
bytes with its own hardware CRC before committing. **Nothing about the payload can be
the cause.** The failure is in the handoff.

## The mechanism, exactly

*verified* from bytes at `abs 0x1c9c8`-`0x1ca68` and `abs 0x17a78`-`0x17b00`.

After the CRC matches and the info record is written, `abs 0x1c9c8` runs:

| Site | Instruction | Effect |
| --- | --- | --- |
| `0x1ca26` | `ldr r1, [r1, #0xc]` | reads `record[0xc]` from `0x20002d70` |
| `0x1ca28` | `cmp` against `0xdbd2`, then `0xdbc3` | proceeds only for a known section flag. Ours was `0xdbc3` |
| `0x1ca44` | `movs r1,#4` / `bl 0x179d8` | reads **four** config words into a stack buffer |
| `0x1ca4c` | `movs r0,#0xc0` / `mvns r0,r0` | builds `0xFFFFFF3F` |
| `0x1ca50` | `str r0, [sp]` | overwrites only `CONFIG0` in that buffer |
| `0x1ca56` | `bl 0x17a78` | erase-and-reprogram the config page |
| `0x1ca62` | `str r0, [r1,#0xc]`, `r0=0x05FA0004`, `r1=0xE000ED00` | `AIRCR` `SYSRESETREQ` |
| `0x1ca68` | `b .` | spin until the reset lands |

The config writer at `abs 0x17a78` is a read-modify-write of the whole config page:

- `lsls r5, r2, #6` with `r2 = 0x5000C000` produces `0x00300000` by 32-bit overflow.
  That is the config aperture, built arithmetically, which is why a literal search for
  `0x300000` finds nothing. Same trap `fwtool.ts` warns about.
- `ISPCMD 0x22` page-erase at `0x00300000`, then `ISPCMD 0x21` programs `CONFIG0`,
  `CONFIG1` (`0x300004`), `CONFIG2` (`0x300008`), `CONFIG3` (`0x30000c`).
- Only `CONFIG0` differs from what was read back. The other three are rewritten
  unchanged.

**So the entire persistent change is `CONFIG0 = 0xFFFFFF3F`.**

`~0xC0` clears bits 7 and 6. On this Nuvoton-derived FMC those are `CBS`, the chip boot
select, and `CBS = 00` means **boot from LDROM**. Every other bit is left at the erased
default of 1, including bit 1, which on NuMicro is `LOCK` and where **0 means locked**.
*derived*: the bit positions are Nuvoton's, applied to a Panchip part. What is
*verified* is the value written and that the firmware changes nothing else.

## Why it did not come back: the LDROM question

**Leading hypothesis: `CBS = 00` points the CPU at an LDROM aperture that has nothing
in it.** *unverified*, and it is the single thing worth checking first.

The confusion this rests on, and it is a real one:

- Nuvoton parts map LDROM to a **separate aperture, `0x00100000`**, not into the main
  `0x0`-`0x3ffff` array.
- Panchip's `section_cfg.h`, which `packages/core/src/ota.ts` mirrors, defines
  `FLASH_BOOTLOADER_ADDR = 0x0003dc00`, which is inside APROM.

Those are two different places. If `CBS = 00` boots `0x00100000` while the vendor's
"bootloader" lives at `0x3dc00`, then setting `CBS = 00` sends the CPU somewhere that
may never have been programmed. Blank flash reads `0xFFFFFFFF`, so the CPU loads
`SP = 0xFFFFFFFF` and `PC = 0xFFFFFFFF` and faults immediately at reset. That is
exactly the observed behaviour: powered, charging, no radio, no LEDs, no button
response.

**This document has always listed the bootloader as unverified and it was never
checked.** `firmware-flashing.md` says so plainly under "Still unverified": *"Whether
the bootloader validates the staged image before copying, and what it does when the
record is absent"*. Committing an OTA depended entirely on that unverified component.

### The corroborating evidence, which was visible in advance

| Signal | Reading at the time | Better reading |
| --- | --- | --- |
| ctrl `01` replied `app=0 dev=0 pro=0` | "suspicious", noted and passed over | the unit's own OTA version struct at `0x20002f80` is zeros. A subsystem never exercised in production looks like this |
| the vendor app refuses an OTA when version major >= 10; ours reports 10 | "the vendor app is not a recovery route for us" | **the vendor deliberately does not OTA these units.** Equally well supported by the same fact, and never considered |

Neither is proof. Together they suggest the OTA commit path on `TR1906R04-10` was
shipped and never used, which is consistent with a missing LDROM image.

## Why the unit is probably still alive

| Claim | Confidence |
| --- | --- |
| The application at `0x16800` was never erased | *verified*. The OTA path only ever erases `0x29400 + offset`, `0x3da00` and the config page. Audited across every FMC site in the image |
| The staged copy at `0x29400` is intact and CRC-correct | *verified*. The device computed that CRC itself and reported a match |
| The part is not read-locked | *derived*. `CONFIG0` bit 1 is 1 in the value written, and `0` is the locked state |
| The fault is one word in the config page | *verified* from the disassembly above |
| Restoring it needs only a page erase, not a computed write | *derived*. Erased `CONFIG0` is `0xFFFFFFFF`, i.e. `CBS = 11` = boot APROM, the factory default |

The last row is the important one. **The fix is to erase the config page and leave it
erased.** No value has to be calculated or invented, which removes the usual danger of
touching `CONFIG0`.

## Recovery plan

Read-only first. Nothing below writes until step 4, and steps 1 to 3 answer the whole
question.

0. **Done.** The case is open and the header is confirmed on our own board: five
   through-holes at **2.54 mm**, on the **LED side**, on the long top edge past the
   antenna notch, order `RST CLK DAT G VD`. See `hardware-access.md`, "The debug
   header".
1. **Attach SWD** to `RST`, `CLK`, `DAT`, `G`. Leave `VD` unconnected and run the
   glasses from their own battery. **No soldering needed**: a 6-pin 2.54 mm pogo probe
   clip fits, and the Debug Probe's JST-SH-to-male-jumper lead plugs straight into it.
2. **Read `0x16800`.** If it matches the decoded stock image, the application is intact
   and this is purely a boot-select fault. If it reads all-`FF` or garbage, the
   bootloader ran and half-wrote APROM, which is still fixable but needs a full
   reflash.
3. **Read `0x00100000` and `0x0003dc00`.** This settles the LDROM hypothesis outright:
   whichever of the two is blank tells us where the boot went. Record both; nobody has
   ever dumped either on this family.
4. **Erase the config page at `0x00300000`** and read back `0xFFFFFFFF`. That restores
   `CBS = 11`.
5. **Reset and see if it advertises.** If APROM was intact, that should be the whole
   repair.
6. If APROM was damaged, program `0x16800` from the decoded stock image. We have the
   exact bytes: `bun research/ota-codec.ts decode firmware/TR1906R04-10_OTA.bin`.

The register sequence does not have to be guessed, because the firmware's own is
*verified*: unlock `SYS_WRPROT` at `0x50000100` with `0x59, 0x16, 0x88`; FMC at
`0x5000c000` with `ISPCON +0`, `ISPADR +4`, `ISPDAT +8`, `ISPCMD +0xc`, `ISPTRG +0x10`;
`ISPCMD` `0x00` read, `0x21` program, `0x22` page erase; poll `ISPTRG` bit 0; failure is
`ISPCON` bit 6. Config writes additionally need `CFGUEN`, `ISPCON` bit 4.

**`hardware-access.md` warns to delete `ISPCON_CFGUEN` from OpenOCD's
`numicro_init_isp()` before building. That advice is for firmware work. This repair is
the one case that genuinely needs `CFGUEN`, because the config page is the thing being
fixed. Set it deliberately, for this one operation, and not by leaving it on.**

## Odds, honestly

Recovery looks good, and the residual risk is execution rather than the device. The
fault is understood, the fix is a single erase to a known-safe default, the part reads
as unlocked, the application was never erased, and we hold the exact bytes for a full
reflash if it was. Against that: nobody has attached SWD to this family before, the pad
mapping is *derived* from FCC photographs rather than seen, and OpenOCD's `numicro`
driver needs a part-ID entry added before it will probe.

The scenarios that would make it genuinely unrecoverable are the ones we have evidence
against: a locked part (`CONFIG0` bit 1 says otherwise) or a disabled debug port (not a
documented `CONFIG0` bit on this family).

## SWD is not just the repair, it is the better flashing route

Worth stating plainly, because "the flashing step failed" invites the wrong conclusion
that firmware work is now blocked. It is the opposite.

The commit path that failed is `stage to 0x29400` -> CRC -> info record -> `CBS = 00`
-> reset -> **unverified bootloader** -> copy to `0x16800`. **SWD writes `0x16800`
directly.** No staging bank, no handshake, no info record, no `CONFIG0` change, no
bootloader. The component that bricked the unit is absent from the path.

It also dissolves the constraint that shaped every design decision so far.
`PROTECTED_REGIONS` in `ota.ts` exists because OTA recovery needs the running
application to bring up BLE and expose `fd00`, so patching the GATT table, the OTA
handler, the flash driver or the descrambler is self-sealing. Over SWD, recovery does
not depend on the application at all.

| Constraint under OTA | Under SWD |
| --- | --- |
| Protected regions are untouchable | all editable; `ota.check` becomes advisory |
| An image that fails to bring up BLE is a brick | re-flash it |
| ~4 minutes per upload, 18-byte packets, ack-driven | seconds |
| The `fd00` service must be preserved | can be stripped |

`firmware/joggles-v1.bin` needs no change. Write `ota.plaintext()` of it to `0x16800`.
Everything verified about that image holds; it was never implicated.

**The asymmetry that matters:** reading flash over SWD needs no driver, because a read
is a plain AHB-AP memory transaction. Writing needs OpenOCD's `numicro` driver with a
part-ID entry added, or direct FMC register pokes from TCL. The second route is now
much easier than it was, because the exact unlock and ISP sequence is *verified* from
the firmware's own code rather than assumed from Nuvoton's.

## What should have been done

- **Own the recovery route before needing it.** `hardware-access.md` called an SWD dump
  "worthwhile insurance" and it was treated as optional. A £12 probe and a flash dump
  before the first commit would have made this a footnote.
- **Never commit on top of an unverified component.** Staging was verified end to end
  on hardware. The bootloader was not verified at all, and the commit handed control to
  it.
- **Treat an unexplained device reading as a stop condition.** `app=0 dev=0 pro=0` was
  seen, called suspicious, and passed over in the same breath.
- **Read a vendor's refusal as information.** The app declining to OTA these units was
  the manufacturer saying something, and it was interpreted only in terms of what it
  cost us.

## Seeing the cause with your own eyes

The whole diagnosis reduces to four read-only commands. None of them can worsen
anything, and together they either confirm this document or overturn it.

    openocd -f research/tools/pan1020.cfg -c "init; halt; \
      mdw 0x00300000; mdw 0x00100000; mdw 0x0003dc00; mdw 0x16800 8; shutdown"

| Read | Expected if this document is right | What it means |
| --- | --- | --- |
| `0x00300000` | **`0xFFFFFF3F`** | `CONFIG0` with `CBS` cleared to 00. **This is the smoking gun**, written by `abs 0x1ca4c` moments before the reset |
| `0x00100000` | `0xFFFFFFFF` | LDROM blank, so `CBS = 00` sent the CPU into erased flash and it faulted at reset |
| `0x0003dc00` | unknown | whatever the SDK calls "bootloader". Nobody has looked |
| `0x16800` | matches `ota.plaintext()` of stock | the application survived, so the fault is purely boot-select and the repair is one erase |

If `0x00300000` reads `0xFFFFFFFF` instead, the config write never happened and
everything above is wrong. That would be worth knowing too.

## Open questions

- Is the LDROM aperture at `0x00100000` on PAN1020, or is it mapped to `0x3dc00`?
  Decides everything above. Answerable by two reads.
- Does anything in the vendor's world ever program LDROM, or do these units ship
  without one?
- Would a `TR1906R04-1-10` unit behave the same? Assume yes until shown otherwise.
- Does the bootloader, if present, restore `CBS`, or is `CBS = 00` the intended steady
  state with LDROM as the permanent entry point?
