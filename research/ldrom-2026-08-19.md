# The bootloader, read at last

**Status:** LDROM disassembled offline from `firmware/ldrom-unit1-2026-08-19.bin`, 9216
bytes, no hardware touched. **Verdict: the bootloader is complete, competent, and it
ran.** It copied the staged image, checked the CRC, promoted the record, restored the
boot select to APROM and reset. Every persistent oddity SWD found on the bricked unit is
its signature, not the application's.

**Scope:** what the bootloader does instruction by instruction, the four physical
fingerprints proving it completed, what it does *not* do, and the answer on
`--ldrom-verified`.

**The answer on `--ldrom-verified` is no.** Reasoning at the end. Keep the bar.

**Three claims in `brick-2026-08-08.md` are wrong**, and this document independently
predicts the result that document's config repair got: `CONFIG0` was never the fault.
Corrections are the first section below.

Two address spaces are in play. The LDROM is linked at `0x00100000` and every address
inside it is quoted that way; `abs` is the flash address in the main dump. The mapping is
flat: `abs = ld - 0x00100000 + 0x0003dc00`. *verified*: the 9216-byte read at
`0x00100000` is byte-identical to `abs 0x3dc00`.

## Corrections to brick-2026-08-08.md

| That document says | Actual | Evidence |
| --- | --- | --- |
| `CONFIG0 = 0xFFFFFFBF` because the app wrote `0xFFFFFF3F` and bit 7 would not take | **The bootloader wrote it.** `ld 0x100b86` builds `~0x40 = 0xFFFFFFBF` deliberately and programs it after erasing the page | *verified* from bytes |
| bit 7 of `CONFIG0` is probably unimplemented | **No evidence for that any more.** The observed value is exactly what shipped code writes, so nothing was refused | *verified* |

**The config repair was always unlikely to work, and this says why.** It ran on
2026-08-19 and did not revive the unit, which is what the disassembly predicts.
`0xFFFFFFBF` is not damage: it is what the vendor's own bootloader programs at the end of
every successful update, *verified* at `ld 0x100b86`. Under Nuvoton `CBS[7:6]` semantics
(*derived*, applied to a Panchip part) `0xBF` is `CBS = 10`, "APROM with IAP", and `0xFF`
is `CBS = 11`, "APROM without IAP". **Both boot APROM.** So erasing the page was never
going to change the boot source, and the device was already booting the application
exactly as the vendor intends.

**One consequence of the repair is worth recording.** The part now sits at `CBS = 11`, out
of IAP mode, which is a state the bootloader never leaves behind. Whether that costs
anything is *unverified*: on NuMicro, IAP mode is what makes the `0x00100000` aperture
executable and readable, so a later read of it may not behave as the first one did.
Restoring `0xFFFFFFBF` is one more config write if it is ever wanted.

**Two read-only measurements, one of them already taken:**

1. **Read the exception frame on unit 1. Done**, and it names the fault: see "The fault
   site, found on the way past" below. `pc 0x00000d38` was never the faulting
   instruction. It is the `b .` at the end of the application's own hard-fault handler,
   sitting directly in front of the string `"In Hard Fault Handler"` at `abs 0xd3c`.
   *verified* from the dump. That handler **prints** all eight frame registers over UART
   before it spins, so a 3.3 V serial adaptor and a power cycle gets the same frame with
   no probe attached.
2. **Read `CONFIG0` on unit 2.** Not done, still cheap, and the only way to learn whether
   `0xFFFFFFBF` or `0xFFFFFFFF` is what a working unit holds.

## What the bootloader does, in order

`main` is `ld 0x100bc8` (`abs 0x3e7c8`). Four calls and then the body:

| Step | Site | What |
| --- | --- | --- |
| 1 | `bl 0x10050c` | unlock `SYS_REGLCTL`, detect the clock, then one GPIO and one clock-enable write. That these are the UART's pin-mux and gate is *derived* |
| 2 | `bl 0x100618` | UART at `0x40100000`, **115200 baud** (`0xe1 << 9 = 0x1c200`) |
| 3 | `bl 0x10054c` | `SYS_REGLCTL` unlock, `0x59` `0x16` `0x88` |
| 4 | `bl 0x1003f0` | `FMC ISPCON \|= 1` (`ISPEN`) |
| 5 | `0x100bd8` | `ISPCON \|= 0x20`, then `\|= 0x08`. Nuvoton names those `LDUEN` and `APUEN`, so **both flash regions are write-enabled**; the bit values are *verified*, the names *derived* |
| 6 | `bl 0x100a88` | the body, below. It never returns; `0x100bee` is an unreachable `b .` |

The body, `ld 0x100a88` (`abs 0x3e688`). All *verified* from bytes.

| Site | What |
| --- | --- |
| `0x100a92` | 512-byte stack buffer A, zeroed |
| `0x100aa2` | **read `abs 0x3da00` into buffer A**, 128 words through `ISPCMD 0x00` |
| `0x100aa8` | `record[0xc] == 0xdbd2`? destination `r4 = 0x00000000` |
| `0x100ab0` | `record[0xc] == 0xdbc3`? destination `r4 = 0x2d << 11 = 0x00016800` |
| `0x100ab6` | **neither: `b .` at `0x100af8`. It hangs forever, silently** |
| `0x100ade` | source is `0xa5 << 10 = 0x00029400`, **hardcoded**, not read from the record |
| `0x100af4` | page count `= (record[0] + 511) >> 9` |
| `0x100afa` | per page: read 512 B from source, **erase the destination page**, write 512 B |
| `0x100b44` | hardware CRC-32 (`ISPCMD 0x2d`/`0x0d`) over `[destination, record[0])` |
| `0x100b54` | compare with `record[4]`. **On match only**, erase `abs 0x3d800` and write buffer A there |
| `0x100b6e` | **erase `abs 0x3da00`**, match or not |
| `0x100b82` | read all four config words from `0x00300000` |
| `0x100b86` | overwrite `CONFIG0` with `~0x40 = 0xFFFFFFBF`, leave `CONFIG1..3` as read |
| `0x100b90` | `CFGUEN`, erase `0x00300000`, reprogram all four |
| `0x100b9c` | `AIRCR = 0x05FA0004`, `SYSRESETREQ`, then spin |

The record's fields, as the bootloader uses them:

| Offset | Unit 1 holds | Used for |
| --- | --- | --- |
| `0x00` | `0x00010224` (66,084) | the page count, and the CRC length |
| `0x04` | `0x04acebff` | expected CRC-32 of the destination |
| `0x0c` | `0x0000dbc3` | destination select. Anything else hangs the part |
| `0x10` | `0x00012c00` | **not read** |
| `0x14` | `0x00029400` | **not read.** The source is hardcoded |
| `0x18` | `0x0000000a` | copied to a stack halfword that nothing reads |
| `0x28` | `0x000a0003` | copied to two stack halfwords that nothing reads |

**The `_INFO` and `_INFO_BACKUP` names in `ota.ts` are the wrong way round in spirit.**
`0x3da00` is the *pending request*: only the application writes it, and the bootloader
consumes and erases it. `0x3d800` is the *installed record*: only the bootloader writes
it, and the application reads it at `abs 0x1f9e4` to populate the version struct at RAM
`0x20002f80` that ctrl `01` reports. *verified* both ways.

## Four fingerprints proving it ran to completion

Each is independent and each is *verified* off `firmware/dump-unit1-2026-08-19-a.bin`.

| Reading | Only the bootloader produces it |
| --- | --- |
| `abs 0x16800` and `abs 0x29400` are identical for **exactly 66,560 bytes**, then diverge | 66,560 is `ceil(66084 / 512) * 512`, the copy loop's page count to the byte. The application never writes `0x16800` |
| `crc32(abs 0x16800, 66084) = 0x04acebff`, equal to `record[4]` | the compare at `0x100b54` passed, which is the only route to the next row |
| `abs 0x3d800` holds the record; `abs 0x3da00` is blank | `0x100b5e` writes the first, `0x100b6e` erases the second. The application does the opposite |
| `CONFIG0 = 0xFFFFFFBF` | `0x100b86` writes exactly this. The application writes `0xFFFFFF3F` |

So the sequence was: application stages, CRCs, writes `0x3da00`, sets `CONFIG0` to
`0xFFFFFF3F` (`CBS = 00`, boot LDROM) and resets; the bootloader boots, copies, CRCs the
copy, promotes the record, erases the request, sets `CONFIG0` to `0xFFFFFFBF`
(`CBS = 10`, boot APROM) and resets; the application boots and hard-faults.

**The bootloader is not the brick.** It did the whole job and handed back correctly.

## The fault site, found on the way past

Not bootloader work, but it fell out of having the dump open. **The full answer now lives
in `research/hardfault-0xd38-2026-08-19.md`**, which took this further; kept here as the
record of how the site was found and because it is what exonerates the bootloader. All
*verified* from `firmware/dump-unit1-2026-08-19-a.bin`.

**The application tail-calls through a RAM function pointer at `abs 0x10f54`:**

    10f54: 4801   ldr r0, [pc, #4]     @ 0x20000014
    10f56: 6e00   ldr r0, [r0, #0x60]  @ *(0x20000074)
    10f58: 4700   bx  r0

The recorded frame matches that instruction pair exactly, and nothing else in the image
produces it:

| Frame | Value | Why this site |
| --- | --- | --- |
| stacked `pc` | `0x6e5cb82a` | the word fetched from `0x20000074` and branched to |
| `r0` | `0x6e5cb82a`, the same | `bx r0` branches to what `ldr r0` just loaded, so the two are equal by construction |
| stacked `lr` | `0x00010e55` | `abs 0x10e50` is `bl 0x10f54`, and a **`bx`** tail call leaves `lr` untouched |
| `pc` when halted | `0x00000d38` | the `b .` closing the hard-fault handler, in front of the string at `abs 0xd3c` |

**`0x6e5cb82a` appears nowhere in the 256 KB dump, at any alignment.** So it is not a
flash value that got misread; it is whatever SRAM at `0x20000074` held. *verified* by a
byte scan of the whole image. That the slot was never written, rather than written and
then corrupted, is *derived*.

`0x20000014` is a hot global in the region below `abs 0x16800`: 51 LDR sites reach it,
and the block at `abs 0x134a8 - 0x13544` looks like the routine that populates its slots.
`abs 0x10f54` has exactly one caller, `abs 0x10e50`, inside the function starting at
`abs 0x10e24`, which fills a struct passed in `r0` at offsets `0x00`, `0x04`, `0x14`,
`0x1c`, `0x20`, `0x24`, `0x28` and `0x2c`. **Offset `0x60` is not among them.**

So the fault is a **RAM problem, not a flash-content problem**, which is consistent with
the config repair changing nothing.

*Corrected 2026-08-19: this said the shape was "a registration-order problem", something
dispatching through slot `0x60` before whatever writes it has run.* **Nothing in the
256 KB ever writes it.** `research/hardfault-0xd38-2026-08-19.md` establishes that, and
concludes the two halves of the flash come from different builds: the application on this
unit never executes the store that would fill `0x20000074`. Read that document for the
repair, which is not a config write.

## What it does not do

- **It does not validate the staged image before copying.** The CRC is computed over the
  **destination**, after the erase-and-write. There is no rollback, no retry and no
  refusal: a corrupt staged image is installed over the running application
  unconditionally, and a CRC failure only means the record is not promoted. *verified*.
  This inverts a line in `firmware-flashing.md`: "the running application is never
  erased" is true of the application's own OTA handler and false of the bootloader,
  which erases and rewrites it page by page.
- **It does not re-validate on any later boot.** It acts only on a record in `0x3da00`,
  and only the application can write one. So a bad image can be superseded by staging a
  good one **if and only if the bad image still runs the OTA service**. If it does not,
  there is no path back except SWD. *verified*. That closes the third item in
  `firmware-flashing.md` "Still unverified".
- **It offers no recovery transport.** The complete peripheral inventory, from every
  resolved literal load in the code region, is: `0x40100000` UART, `0x50000100`
  `SYS_REGLCTL`, `0x50000200` clock control, `0x50004040` one GPIO config write,
  `0x5000c000` FMC, `0xe000ed00` SCB. No radio. No GPIO **read**, so no button check. The
  UART is loaded at exactly two sites, `putchar` and `uart_init`, so it is **transmit
  only**: there is no receive polling and no UART ISP path, despite Panchip's
  `DFU_SOURCE_UART = 2`. *verified*. That closes the second item in "Still unverified".
- **It runs with interrupts effectively disabled.** Every vector except reset and
  HardFault points at a distinct `b .` in `0x100208..0x100213`. *verified*.
- **It says nothing on a normal boot.** The UART it brings up is used only by the fault
  handler at `0x1004e4`, which prints `"In Hard Fault Handler"` and eight registers, then
  spins. Silence on the wire during an update is expected, not a symptom.

**An unrecognised flag is a silent hang.** `0x100af8` is a bare `b .`: no output, no
timeout, no fallback to booting the application. Combined with the erase of `0x3da00`
this cannot happen twice in a row from a normal update, but it is what a torn or
mis-written record buys, and it is the fourth answer "Still unverified" was waiting for.

## A capability worth knowing about

The bootloader is a working, *verified* flash programmer that can be driven with two very
small writes, and on unit 1 the ammunition is already loaded: `abs 0x29400` still holds a
plaintext copy of the stock application. Write a 512-byte record to `0x3da00` with
`[0x00] = 0x00010224`, `[0x04] = 0x04acebff`, `[0x0c] = 0x0000dbc3`, set
`CONFIG0 = 0xFFFFFF3F`, reset, and it will erase and rewrite `0x16800` from the staging
bank and restore the boot select itself.

Two caveats before anyone reaches for it. It would install bytes that are **already
there**, so on unit 1 today it fixes nothing. And it still needs FMC pokes over SWD to
write those two places, which is the same capability that would let SWD write `0x16800`
directly. It is a fallback worth having recorded, not a shortcut.

## Can `--ldrom-verified` be passed? No

The flag's literal condition is now met and its purpose is not, and the purpose is what
it is for.

**Met:** the LDROM has been dumped, it holds a real bootloader, and that bootloader
restores the boot select to APROM. `firmware-flashing.md` says the flag needs "an LDROM
dump over SWD, showing a bootloader that restores `CBS`". Taken literally, that is done.

**Not met, and this is what matters:**

- **The brick is located but not explained.** The bootloader is exonerated, the image is
  byte-identical to stock, the boot select is correct, the config page has been restored,
  and the unit still hard-faults through an uninitialised RAM pointer at `abs 0x10f54`.
  Nothing yet says why the boot path reaches that dispatch early, so committing again
  would repeat an experiment whose outcome we cannot predict. One unexplained device
  reading was already treated as a footnote once, and it cost a unit.
- **The path is worse than it was assumed to be, not better.** It copies before it
  validates, over the running application, with no rollback. A commit is a one-way door
  and the door has no handle on the far side.
- **The bootloader has no recovery transport at all.** No UART receive, no button, no
  radio. If the installed image fails to bring up BLE, SWD is the only way back, so a
  commit is only ever as safe as having a probe already attached.
- **An unrecognised record hangs the part silently**, with no output and no fallback.
- **Nothing needs this path.** SWD writes `0x16800` directly and skips staging, the
  record, the config write and the bootloader entirely. The component that is now
  understood is also the component we no longer have a reason to use.

**What would genuinely support passing it**, in order:

1. Explain the fault at `abs 0x10f54`: find what writes `0x20000014 + 0x60` and what
   selects the branch that reaches `abs 0x10e50`. The frame is read; the mechanism is
   not, and until it has a name no commit is predictable.
2. Read `CONFIG0` on unit 2 and settle whether `0xFFFFFFBF` is the shipped value.
3. Run one full commit end to end on a unit that has been dumped first, with SWD attached
   and a repair rehearsed, on an image that has passed `ota.check`.
4. Only then lift the bar, and only for units with a probe attached.

Step 1 is offline work on material already in hand. Step 2 is read-only and costs a
minute. Neither has been done.

**Suggested wording change, not made here:** the flag's condition in
`packages/cli/src/flash.ts` and in `firmware-flashing.md` step 4 asks for something that
is now satisfied while the danger it stands for is not. If the bar stays, it should ask
for what it means: that a commit has been proven survivable on a unit that can be
recovered.

## The debug console: which UART, which pin, what it says

**Conclusion: the fault print comes out of UART0 on P1.3, which is pin 11 of the QFN32.
115200 8N1. It is not the panel's UART, and it is not on the debug header.** The
bootloader and the application drive the same peripheral with the same settings, so one
tap reads both. The cost is that P1.3 is a bare 0.5 mm QFN pin: neither labelled pad group
on the board is known to carry it, and nobody has looked.

### The two UARTs are different peripherals, and it is not close

Every field below is *verified* from bytes, at the sites named.

| | Debug console | LED panel |
| --- | --- | --- |
| Base | `0x40100000` (UART0) | `0x40101000` (UART1) |
| Pin mux | `SYS[0x34] \|= 0xC00` | `SYS[0x38] \|= 0x30` |
| Pins | **P1.2 RXD, P1.3 TXD** | **P2.4 RXD, P2.5 TXD** |
| QFN32 pins | **10, 11** | 22, 23 |
| GPIO block touched | `0x50004040` (P1) | `0x50004080` (P2) |
| Clock gate token | `0xa7803d10` | `0xa7803d11` |
| Bootloader sites | `ld 0x100524`, `ld 0x100618` | never touched |
| Application sites | `abs 0x1fd4a`, `abs 0x1fd70` | `abs 0x1815e`, `abs 0x18188` |

**So tapping the console does not go anywhere near the panel ribbon**, and no frame data
appears on it. The two differ in base address, mux register, mux bits, GPIO port and
clock-enable token, which is four independent ways of being separate peripherals.

### How the pin was resolved

The mux value is the whole proof, and it is exact rather than inferred.

Panchip's `sys.h` encodes a pin's function as three bits spread across one 32-bit register
per port: `MFP` at bit *n*, `ALT` at bit *n*+8, `TYPE` at bit *n*+16, eight pins per port.
The header then names each combination:

| SDK constant | Value |
| --- | --- |
| `SYS_MFP_P12_UART0_RXD` | `0x00000400` |
| `SYS_MFP_P13_UART0_TXD` | `0x00000800` |
| both together | **`0x00000C00`** |
| `SYS_MFP_P24_UART1_RXD` | `0x00000010` |
| `SYS_MFP_P25_UART1_TXD` | `0x00000020` |
| both together | **`0x00000030`** |

`0xC00` is what the bootloader and the application each write to `SYS[0x34]`, and `0x30`
is what the application writes to `SYS[0x38]`. The values are the SDK's own constants,
unmodified, so `SYS+0x34` is `P1_MFP` and `SYS+0x38` is `P2_MFP`. *verified* against
`src/platform/driver/inc/sys.h` in the SDK mirror `firmware-flashing.md` already cites:

    https://raw.githubusercontent.com/hao0527/BLE_APP/master/src/platform/driver/inc/sys.h

The GPIO write corroborates it. Both console initialisations clear bit 18 of
`0x50004044`. GPIO port blocks are `0x50004000 + 0x40 * port`, so that is **port 1**,
register `+4` is `OFFD`, and its bit *n*+16 is the digital-input disable for pin *n*.
Clearing bit 18 re-enables the input path on **P1.2**, which is the RX pin. The panel
does the same thing to bit 20 of `0x50004084`, i.e. **P2.4**, its RX pin. Two ports, two
pin numbers, both matching their own mux. *verified*.

Package pins come from the PAN1020 datasheet pin table, `QFN32 | QFN48 | SSOP24`:

| Signal | QFN32 | Cross-check |
| --- | --- | --- |
| `NRESET_PAD` | 1 | matches `hardware-access.md` |
| `P5.2` `INT1` | 2 | the button, *verified* by hand-decode in `CLAUDE.md` |
| `P4.6` `ICE_CLK` | 3 | matches `hardware-access.md` |
| `VDD1`/`VDD3` | 4 | matches `hardware-access.md` |
| `P4.7` `ICE_DAT` | 5 | matches `hardware-access.md` |
| `P5.3` `ADC_CH0` | 8 | the battery gauge, `firmware-internals.md` |
| `P1.2` `UART0_RXD` | **10** | |
| `P1.3` `UART0_TXD` | **11** | |
| `P2.4` `UART1_RXD` | 22 | |
| `P2.5` `UART1_TXD` | 23 | |

Six of those ten were already known from two other sources and all six agree, so the
table is being read correctly. Our SoC is the QFN32: `U2`, die marking `25170Da`,
*verified* in `hardware-access.md`.

**This upgrades two claims in `firmware-internals.md` from *derived* to *verified*.**
"UART0 ... P1.2/P1.3. Debug console" and "`SYS->P2_MFP |= 0x30`, putting TX/RX on
P2.4/P2.5" were both right. The direction is now pinned too: **P1.3 is TX, P1.2 is RX.**

### Baud and framing

`0xe1 << 9 = 115200`, built identically in both, at `ld 0x10061a` and `abs 0x1fd66`. The
byte written to offset `+4` of the init struct is `3`, and the SDK's `uart.h` defines
`Uart_line_8n1 = 0x03`. So **115200 8N1**. No flow control: the `RTS`/`CTS` alternates
exist on other pins and are never muxed. *verified*.

### What ever prints, and how noisy the line is

Three separate printf implementations exist in the device, and all three write to UART0.

| Where | printf | Call sites | What they are |
| --- | --- | --- | --- |
| Bootloader | `ld 0x1006c0` | 9 | the fault banner and its eight registers. Nothing else |
| Region below `abs 0x16800` | `abs 0x1398` | 17 | two register-dump blocks. Nothing else |
| Application | `abs 0x1887c` | 32 | 26 are three register-dump blocks; six are traces |

The six application traces are the only routine output, and none is on a rendering path:

| Site | Text |
| --- | --- |
| `abs 0x191e0`/`0x191ec` | `0x%02X ` in a loop of 8, then a newline. One caller, gated |
| `abs 0x1cd4a` | `send enc cmd completed,status:%d` |
| `abs 0x1ceea` | `READ CON PARAM` |
| `abs 0x1e478` | `gattc_send_svc_changed_cmd_handler` |
| `abs 0x1fc1c` | `recv %d`, in a function reached only as a registered callback |

**So the line is near-silent**: a few short BLE lifecycle lines around a connection, and
otherwise nothing until something faults. The bootloader in particular prints nothing at
all on a normal update, so silence during a commit is expected and says nothing.

**The handler that actually ran on unit 1 is the one below `abs 0x16800`**, because the
CPU's HardFault vector at `0x0c` points to `0xd5` and the application cannot relocate it
(Cortex-M0 has no `VTOR`). It prints the same nine lines through `abs 0x1398`, on the same
UART. *verified*.

### Clipping to it, in practice

**The honest headline: P1.3 is not on a labelled pad.** The debug header is
`RST EK ED G VD` and carries no UART. The other group, `V+ G K VD`, reads as power, but
`K` is unexplained and is worth two seconds with a continuity meter before anyone reaches
for a soldering iron. So is the pair of wired pads at the far end of the board that
`hardware-access.md` mentions. Failing those, this is a bare QFN pin.

| | |
| --- | --- |
| Signal | `P1.3`, UART0 TXD, **QFN32 pin 11** |
| Where it is | bottom edge of `U2`. Pins 1-8 run down the left side from the dimple, 9-16 along the bottom, so pin 11 is the **third pin along the bottom edge** |
| Pitch | 0.5 mm on a 5 x 5 mm package. **Not clippable.** A fine-tip probe held on the pin, or 34-38 AWG wire tacked to it |
| Ground | the `G` pad on the debug header, or `G` on the `V+ G K VD` group |
| Adaptor | 3.3 V logic. Adaptor **RX** to pin 11. Leave the adaptor's TX and VCC disconnected, and run the glasses from their own battery |
| Settings | **115200 8N1**, no flow control |
| Healthy unit | near silence, then a line or two such as `READ CON PARAM` when a phone connects |
| Unit 1 | on power-up: `In Hard Fault Handler`, then `r0 = 0x6e5cb82a` through `psr = 0x...`, then nothing. `pc` should read `0x6e5cb82a` and `lr` `0x10e55` |

Do not connect the adaptor's TX to P1.2 casually. Nothing in the bootloader reads it, and
what the application does with received bytes has not been traced.

**Nothing on this line has ever been observed.** The chain is *verified* at every link
from firmware bytes to SDK constants to the datasheet pin table, but no instrument has
been attached, so the first capture is still the thing that proves it. If pin 11 turns out
to be unrouted on this board, the pin itself is still the signal and a tacked wire still
works.
