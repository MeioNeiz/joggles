**Status:** answered offline from `firmware/dump-unit1-2026-08-19-a.bin` and
`firmware/sram-unit1-2026-08-19.bin`. No hardware touched. **Revised once, on the same
day, after live silicon contradicted part of the first version.** The corrections are the
second section and they are the most useful part of this file.

**Verdict: the application in flash never writes callback slot `+0x60`, and the BLE stack
calls out through it on the cold-boot path. `CONFIG0` was never involved.** The RAM struct
the stack reads is a **fossil**: it still holds the pointers the unit's original firmware
wrote before the OTA, retained in SRAM across every reset since 2026-08-08. Those pointers
are all wrong for the image now in flash, by 0x2f0 to 0x490 bytes each.

**The unit therefore has two failure modes, one per boot path, and the same cause:**

| Boot | Path taken | What happens |
| --- | --- | --- |
| cold | `abs 0x1c814`, full init | chip init reads slot `+0x60`, gets uninitialised SRAM, `bx` faults |
| warm | `abs 0x1c8f0`, wake | chip init never runs, so nothing faults. The app runs on the fossil and the radio never comes up |

**The repair is unchanged and is now much better evidenced: put the unit's own application
back, which means reading unit 2 over SWD.** Two independent fossils of the original
firmware survive on this unit and both say the image we wrote is a different build.

**Scope:** what was got wrong and why, where the registration actually lives, the proof
that the struct is a fossil, the two boot paths, why BLE is down, and what to do. The
bootloader's side is `research/ldrom-2026-08-19.md` and is not repeated.

Offsets are `abs` flash addresses.

**What survives, and is now confirmed from silicon rather than inferred:** slot `+0x60`
has no writer in this image, and the four slots `+0x5c`, `+0x60`, `+0x64` and `+0x68` are
exactly the ones the original firmware filled and this one does not.

on this core cannot be classified from registers at all. The UART print at `abs 0xcf0` is
the only route to a classification.

## Where the registration lives

*verified* from bytes. The registrar is `abs 0x190a4`, one caller, `abs 0x20650`, reached
from the cold-boot path only.

| Site | What it does |
| --- | --- |
| `0x190a6` | `movs r4,#0xb3` / `lsls r4,#9` = `0x16600`, the stack's export table, built arithmetically |
| `0x190aa`-`0x19102` | fifteen `ldr r1,[r4,#n]` / `ldr r0,[pc]` / `blx r1` pairs: slots `+0x04` to `+0x3c` |
| `0x19104` | `r4 = 0x16640`, this one a plain literal, which is why the first pass saw only this half |
| `0x19106`-`0x19128` | six more: slots `+0x40` to `+0x54` |
| `0x1912a`-`0x19130` | `r5 = 0x16700`, then export `0x1672c`: slot `+0x58` |
| `0x19138`-`0x19156` | four `set_isr` calls, indices **10, 16, 9, 6** |
| `0x19158` | returns |

**It stops at `+0x58`.** Exports `0x16764` and `0x16768`, the setters for `+0x5c` and
`+0x60`, are never called, and neither are `0x166ac` and `0x166b0` for `+0x64` and `+0x68`.
Read instruction by instruction, twice. So the original finding stands where it counts.

The same is true of the other stock container: *verified* by decoding both and running the
export scan on each, neither `TR1906R04-1-10` (appVer 1) nor `TR1906R04-10` (appVer 3)
registers `+0x5c` or `+0x60`. **Either would have bricked the unit the same way**, so this
was never a wrong-variant mistake.

## The struct in RAM is a fossil, and that is the proof

The live read shows all 27 slots populated with plausible pointers except `+0x00`. That
looked like it refuted the finding. It does the opposite: **not one of them is a value
this image would write.**

*verified* by comparing the registrar's own literal pool at `abs 0x1915c` with the SRAM
capture, slot by slot.

| Slot | This image writes | RAM holds | Delta |
| --- | --- | --- | --- |
| `+0x04` | `0x000193ad` | `0x0001969d` | `0x2f0` |
| `+0x10` | `0x0001a609` | `0x0001a929` | `0x320` |
| `+0x14` | `0x0001d629` | `0x0001d9dd` | `0x3b4` |
| `+0x18` | `0x0001ee9d` | `0x0001f291` | `0x3f4` |
| `+0x20` | `0x0001fe61` | `0x00020279` | `0x418` |
| `+0x58` | `0x000203ad` | `0x0002083d` | `0x490` |
| `+0x5c` to `+0x68` | **nothing** | `0x0001cb7d`, `0x00020805`, `0x00020791`, `0x0001cc75` | n/a |

All 22 registered slots differ. Zero match. Sorted by flash address the deltas are
`0x2f0 0x304 0x320 0x320 0x320 0x3b4 0x3b4 0x3f4 x8 0x418 x6 0x490`: monotonically
non-decreasing, a few hundred bytes, growing with address. **That is what the same source
compiled into a slightly larger binary looks like**, not corruption and not chance.

The interrupt table at `0x20000080` says the same thing independently and more sharply.
The registrar installs exactly four handlers, at indices 10, 16, 9 and 6. In the SRAM
capture **those four indices, and only those four, hold code pointers**; every other index
in the first twenty is random:

| Index | This image installs | RAM holds | Delta |
| --- | --- | --- | --- |
| 6 | `0x00017ef9` | `0x00017fb5` | `0xbc` |
| 9 | `0x0001874d` | `0x000189b5` | `0x268` |
| 10 | `0x0001877d` | `0x000189e5` | `0x268` |
| 16 | `0x000174d5` | `0x000175c9` | `0xf4` |

Four hits out of twenty, on precisely the four indices this application's registrar uses,
with values shifted the same way. **The registration was done by a different build of this
same application, and it has been sitting in SRAM ever since.** The OTA's handoff reset was
`SYSRESETREQ`, which does not clear SRAM, and the unit has been on its battery throughout.

Two consequences follow immediately:

- **The registrar has not run on the current boot.** If it had, all 22 slots would hold the
  flash values.
- **The original firmware did register `+0x5c` through `+0x68`.** The fossil has valid
  pointers there and this image has no code that could put them there. That is the
  export-89/90 finding, confirmed from the device rather than inferred from a scan.

## The two boot paths

*verified* at `abs 0x1f86c`, the application's `main`.

```
1f86c  bl 0x16824            ; restore MSP to the stack's 0x20002648
1f870  ldr r0,=0x50001000 ; ldr r0,[r0,#0x30] ; test bit 15
1f878  beq 0x1f880
1f87a    bl 0x1c8f0          ; path A, wake
1f880    bl 0x1c814          ; path B, full init
```

`bl 0x16824` explains the `msp 0x20002648` seen on both captures: the application starts on
its own stack at `0x20003910` and hands itself back to the stack's stack before `main`
proper. The 160 bytes below it in the faulted capture are the exception frame plus two
frames, which is the correct depth for `chip init -> 0x13f9c -> 0x10e24`.

| Path | Entry | Calls the registrar? | Calls chip init `abs 0x143a8`? | Reads slot `+0x60`? |
| --- | --- | --- | --- | --- |
| B, full init | `0x1c814` | **yes**, via `0x2060c` then `0x20650` | **yes**, at `0x1c85c` | **yes** |
| A, wake | `0x1c8f0` | no | no | no |

Bit 15 of `0x50001030` selecting cold from warm is *derived*: `0x50001000` is the clock and
power controller, the application reads `+0x1c` of it elsewhere for the same kind of
question, and the two paths are shaped exactly like full-init and resume-from-retention.

## Reconciliation: both observations, one cause

Nothing here is intermittent. Each path is deterministic; the two captures are two paths.

| Capture | Path | Slot `+0x60` held | Outcome |
| --- | --- | --- | --- |
| the halted HardFault, `pc 0xd38` | B | `0x6e5cb82a`, cold SRAM | `bx` to an odd-numbered non-address, immediate fault |
| the running Thread-mode capture | A | `0x00020805`, the fossil | never read. Runs, and the radio never comes up |

The faulted frame corroborates the site exactly: `r0` and the stacked `pc` are both
`0x6e5cb82a`, which is what `bx r0` at `abs 0x10f58` produces and nothing else does, and
the stacked `lr` is `0x00010e55`, the return address of the `bl` at `0x10e50` that a **tail
call** leaves untouched. `xPSR 0x60000000` puts the faulting context in Thread mode.

So the honest statement of the defect is:

> This application never writes slot `+0x60`. On the path that reads it, what the CPU
> branches to is whatever SRAM happens to hold: random after a true cold start, and a
> pointer into a different build's layout after a retained one. Neither is right.

## Why BLE is down on the running unit

Two independent reasons, both consequences of being on path A with a fossil.

1. **Nothing has initialised the radio on this boot.** Chip init `abs 0x143a8` is called
   only from `abs 0x1c85c`, on path B. Path A assumes the previous session left the
   hardware and RAM configured, and here the previous session was different firmware.
2. **No interrupt handler is installed for this image.** The four `set_isr` calls live in
   the registrar, which has not run, so the RAM vector trampolines at `0x20000080` still
   point into the old build. Any enabled interrupt trampolines into the wrong code. The
   unit is one interrupt away from the same class of fault it was in before.

Every callback the stack makes on path A goes through the fossil, so advertising is not
merely unstarted, it is unreachable. *derived*, but there is no competing reading.

## What to do

Unchanged from the first version, and now on firmer ground. Steps 1 and 2 are read-only.

1. **Dump unit 2 over SWD, read-only.** `swd-recon.sh dump`. Still the single
   highest-value action: it is the only surviving copy of the application that matches this
   stack, it settles whether the two units' `0x0`-`0x167ff` are identical, it gives a
   healthy `CONFIG0`, and it makes unit 2 recoverable, which it is not today.
2. **Compare.** `dumpcheck` unit 2 against the vendor plaintext. Predictions, all now
   sharp enough to falsify this document: unit 2's `0x16800` does **not** match the APK
   image; its application runs past `0x26c00`; its registrar covers slots `+0x5c` to
   `+0x68`; and its handler addresses match the fossil in unit 1's SRAM, allowing for
   whatever the build difference is.
3. **Write unit 2's `0x16800`-`0x293ff` to unit 1.** That restores the matching application
   and the orphan data region together. Do not copy `0x3c000`, the info pages, or the
   staging bank.
   - The advert name looks safe to copy: `GLASSES-` is a literal in the application's
     `.data` source at `abs 0x26918` and the suffix comes from the per-chip value read
     through `ISPCMD 0x04` at address `0x58`. *derived*; confirm against unit 2's dump
     before writing.
4. **Do not bother patching `abs 0x10f54` to `bx lr`.** The first version suggested it as a
   fallback. It would stop the cold-boot fault and change nothing else: the other 22 slots
   would still be wrong on path A and the four unregistered ones would still be wrong on
   path B. It buys one UART line of information at the cost of a flash erase.

## What this changes elsewhere

- **`firmware/joggles-v1.bin` must not be flashed to either unit as it stands.** It is
  built on the APK's `TR1906R04-10` image and carries the same mismatch, so writing it to
  unit 2 over SWD would put unit 2 in exactly this state. `build-firmware.ts` needs to base
  the patch on **unit 2's own application image**.
- **The gate that matters is not `--ldrom-verified`.** The bootloader worked. The gate that
  would have saved the unit is "the image being committed is the image this unit is
  running", and nothing in `ota.check()` tests it. The vendor app's refusal to OTA
  `devVer >= 10` was that gate, and it was read as an obstacle.
- **`research/firmware-internals.md` and the bank documentation describe the APK image**,
  which is now known to differ from what the hardware runs. Nothing in them is thereby
  wrong, but "the firmware" in those files means "the firmware in the APK" until unit 2 is
  dumped.
