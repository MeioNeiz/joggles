# The scroll-loop gap: session versus power-cycled (track 16, 2026-08-10)

Why the app preview loops tightly while the panel shows a long dark gap between
passes. Session cut short by usage limits; the one pending observation is named at
the bottom. Judgement and next steps: `.claude/locks/track-16`.

## What was observed

- The complaint: preview loops seamlessly, panel leaves a gap "as if space for the
  max looping length of text" (Jacob, by eye, on saved scrolling text).
- 2026-08-10, `bun run packages/cli/src/loopgap.ts run --yes` on `GLASSES-125B37`:
  saved a solid 32x9 type 1 block (nonce in dead pixels), `DATCPOK`, 11 lifetime
  saves, `SPEED 5`, `MODE 02 00`, disconnected. **Jacob watched it loop seamlessly:
  no dark pass at all.** *verified*, one run, same session as the save, no power
  cycle. This refutes any model where the 48 bracket columns are walked in-session.

## The wire archaeology

`packages/app/.expo/dev/logs/start.log` decodes with the vendor key (decoder:
scratchpad `decode-expo-log.ts`, session 7c701f79; rebuild it from `p.decrypt` over
the `ble > <char> <hex>` lines if needed). The save behind the original complaint:

    21:17:11  DATS 01 00 66      102 bytes announced
    21:17:12  DATCP              payload = 51 columns, 24 trailing blank, type 1
    21:17:12  SPEED 50, MODE 02 00

So that content was 27 columns of text plus the 24-column client gap that
`content.text()` appends by default for scroll (`gap = COLS`, `content.ts:222`).

## The model that fits everything so far

- `research/firmware-internals.md` "Type 1 gets 24 blank columns at each end,
  free": `DATS` starts type 1's counter at 48, `DATCP` records `ncols = N + 48`
  (`abs 0x1833e`). *derived*, still trusted for the record layout.
- **In the session that saved, `MODE 02` loops the bare content width N.**
  *verified* today (the seamless solid block).
- **After a power cycle the device restores from the flash record and walks
  `N + 48`**, putting 24 blank columns each side into the loop. *derived*, not yet
  observed - this is the pending test. It would explain the original complaint
  exactly: 51 saved columns -> post-cycle loop of 99 with a 72-column blank run
  (24 client gap + 48 bracket), ~6.9s of dark every ~13.9s at the default speed.

## The pending observation

Power-cycle the glasses (2s button hold, then on) with the solid block saved, and
watch. Speed resets to the firmware default (divisor 7, 140ms/column). The marker
is the missing-pixel nonce pattern in the bottom row.

    bracket appears (model holds)   DARK ~3.5s, marker period ~11.2s
    still seamless                  record ncols unused; the original gap needs
                                    another explanation entirely
    dark ~minutes                   scroll walks the whole store; model wrong

Jacob may already have run this; the answer was not recorded before the session
stopped. If unknown, re-run: the block persists in flash, the test costs nothing.

## Consequences once the pending half lands

- `content.text()` should default `gap` to 0 for scroll: the persistent loop
  already carries 48 blank columns, and the client gap only lengthens the dark
  pass. (One `dats.ts` edit exporting `TYPE1_BRACKET = 24` is already in the
  working tree, docblock included.)
- Previews must simulate the post-cycle loop: content bracketed by 24 blank
  columns each side, wrapping at N + 48. Planned as `viewport.marqueeAt` /
  `marqueeOffsets`, wired into `viewport.frames()` and `app/src/Preview.tsx`.
- `effects.ts`'s premise "the device wraps the buffer and the join is as visible
  as any other column" fails post-cycle: every type 1 loop gains a 48-column
  black band. `loopSeconds()` is short by 48 columns. Seamless wide loops on
  stock firmware are only seamless until the first power cycle; a JGX sub-command
  patching the wrap bound could restore them.
- The in-session and post-cycle loops genuinely differ by 48 columns and nothing
  client-side can reconcile them; the app should preview the persistent state.
