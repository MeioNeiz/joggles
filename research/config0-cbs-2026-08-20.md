# `CONFIG0` on unit 1: the only unit at `CBS = 11`, and why it turned out not to matter

**Asked and answered the same day. `CBS` does not gate application-driven ISP, so unit 1
being the only unit at `CBS = 11` does not stand in the way of Track C, and the config page
should be left alone.** The resolution is `research/fmc-primitives-donor-2026-08-20.md`
section 5; this file is the question, the reading it came from, and the two things it got
wrong on the way.

The question was worth asking. `CBS = 11` is "APROM without IAP mode", IAP is
in-application programming, and the resident updater is the only thing this project has
ever built that writes flash from the running application. Unit 1 is the Track C target.
That is a real adjacency and nobody had looked at it.

*Corrected 2026-08-20, twice, and both corrections make the finding smaller:*

1. *This file first said the question was open and settled only by reading a third unit or
   at the bench. It closed offline the same session, from the vendor's own bytes.*
2. *It said the failure mode would look like success. **That was wrong**, and the reason it
   is wrong is a property of our own code that was already there: see "The silent failure
   was never reachable".*

Context: `research/aprom-write-2026-08-20.md` is the repair that left this state,
`research/ldrom-2026-08-19.md` is where `CBS` was first decoded, and
`research/fmc-erase-program.md` has the register-level detail.

## Confirmed on live silicon, late 2026-08-20

The table below was read off dump files. It has since been read off the **running part**
through the probe, and it agrees exactly:

    0x00300000: ffffffff 00000000 00000000 0003dbff

So `CONFIG0 = 0xffffffff` on unit 1 is *verified* on silicon, not merely in a dump, and
`CONFIG1` to `CONFIG3` match every other reading. Also read in the same pass:
`0x00100000` and `0x0003dc00` both give `0x20000610`, so the LDROM aperture is an alias
of the bootloader's base, which is what `research/ldrom-2026-08-19.md` assumed.

Nothing was written. The verdict below is unchanged: `CBS` does not gate
application-driven ISP, so this is still a difference to leave alone.

## The reading

*verified* offline, 2026-08-20, from the dumps on disk. The config page is physically the
last 512-byte page of the main array and the `0x00300000` aperture is a view of it, so
these are byte reads at file offset `0x3fe00` and no device was touched:

| Dump | `CONFIG0` | `CONFIG1` | `CONFIG2` | `CONFIG3` |
| --- | --- | --- | --- | --- |
| `dump-12E69E-2026-08-19-a.bin` (healthy donor) | `0xffffffbf` | `0x00000000` | `0x00000000` | `0x0003dbff` |
| `dump-unit1-2026-08-19-a.bin` (unit 1, pre-repair) | `0xffffffbf` | `0x00000000` | `0x00000000` | `0x0003dbff` |
| `dump-unit1-2026-08-20-after.bin` (unit 1, post-repair) | **`0xffffffff`** | `0x00000000` | `0x00000000` | `0x0003dbff` |
| `dump-unit1-2026-08-20-postcycle.bin` (unit 1, after a power cycle) | **`0xffffffff`** | `0x00000000` | `0x00000000` | `0x0003dbff` |

The value survives a power cycle, so it is the state the part boots in rather than a
transient, and `CONFIG1` to `CONFIG3` are identical everywhere, so `CONFIG0` is the whole
difference. `0xffffffbf` is `CBS = 10`, `0xffffffff` is `CBS = 11`, both boot APROM, and
the unit works.

## Why `CBS` does not gate it

Four legs, from `research/fmc-primitives-donor-2026-08-20.md`. The third is the one that
actually closes it, and it needs no device.

1. **The refusal list does not mention `CBS`.** The vendor header enumerates nine
   conditions that set `ISPFF`, and it demonstrably includes both a `CONFIG0`-dependent
   refusal (`LOCK`, by name) and a mode-dependent one (`DFEN`, via "address illegal"). The
   model is closed: the operation is "not started, and the fail flag set instead". `CBS` is
   absent from it.
2. **Every documented `CBS` effect is the reset-latched address map.** "IAP mode" is the
   arrangement where APROM code *calls the LDROM's own* ISP routines, and `CBS[0] = 1`
   unmaps the LDROM. Our updater calls nothing, and its `GUARD` bounds every `ISPADR` to
   `[0x29400, 0x2d400)`, main array, mapped under all four encodings. The only region
   `CBS` remaps is the one the updater structurally cannot address.
3. **`CBS` is not read live from the config page**, *verified* from donor bytes. The
   vendor's own OTA handoff at donor `0x1cdb0`-`0x1cdf8` erases the config page and then
   programs four words into it. Between the erase and the first program, the page reads
   `CBS = 11`. If the ISP engine consulted `CBS`, the vendor's own commit path would fail
   on its own second word.
4. **Three of the four latch/requester combinations are already witnessed on silicon.**
   `CBS 00` with LDROM code (the bootloader's 130 pages), `CBS 10` with APROM code (OTA
   staging, and the config write above), and `CBS 11` with the debugger (2026-08-20:
   `dump-unit1-2026-08-20-partial.bin` reads `CONFIG0 = 0xffffffff`, so the latch was
   already 11 during that write). Only `CBS 11` with APROM code is unwitnessed, nothing
   makes the requester visible to the FMC (a trigger is an APB write either way), and the
   one input that *does* see the debugger, "Page Erase at LOCK mode with ICE connection",
   makes the debugger the **restricted** party. So the run we have is the stricter case.

Verdict *derived*, on four legs, and the residual is only the requester.

## The silent failure was never reachable

This file originally argued the cost of being wrong was an expensive afternoon: the
updater flashed, `HELLO` answering, `UPD_BEGIN` reporting success, and every erase
silently writing nothing. **That was wrong, and the code already prevented it.**
`erase_page` reads the whole page back and requires all-ones, `program_word` compares
every word, and `upd_begin` returns `UPD.FMC_REFUSED` the moment `erase_span` fails. A
`CBS`-gated refusal therefore comes back as `FMC_REFUSED` on the very first frame. The
updater cannot report OK on a write that did not happen.

So the bench cost of the whole question, had it gone the other way, was **one reply code**.
Worth recording, because the mistake was to reason about a hazard without first checking
what our own error paths already caught, and that is a cheap habit to get wrong again.

## Leave the config page alone

Nothing now argues for writing it, and there is a standing argument against.

Restoring `0xffffffbf` from `0xffffffff` means setting bit 6 to 0, which is a **program**,
not an erase, and a config program requires `CFGUEN` set.
`research/fmc-erase-program.md` lists the `CONFIG0` `LOCK` bit as "the one permanent path"
and closed, on two legs: `CFGUEN` clear all session, and an erase cannot drive a bit to 0.
**Both legs are gone in this direction.** The 2026-08-19 change was incapable of locking
the part; its reversal would be the first operation in this project that could.

`research/fmc-erase-program.md` also records an unexplained reading in the same page:
`CONFIG2 = 0x00000000` where the PAN1020 manual's `ALOCK` latch is said to require `0x5A`,
on both units, unresolved. Programming a page while one of its words is not understood is
worse than leaving it.

`research/tools/fmc-repair-config.sh` was turned round to this direction before the
question closed. It is set up correctly and it refuses to run without `--cbs-checked`,
whose homework is now **done and came back "no reason to write"**. Treat the flag as
spent rather than as a step to complete.

## If anyone wants the last leg anyway

Two ways, neither needed:

- **One DATS type 1 save to unit 1.** Unit 1 runs the stock donor application booted at
  `CBS = 11`, so an ordinary save is the vendor's own code performing IAP at `CBS = 11`,
  which is exactly the unwitnessed combination. `.joggles/ledger.json` holds records for
  `GLASSES-125B37` only, so it has never been done on unit 1. No probe move, no config
  write, and none of our code involved. Costs five page erases of someone else's wear
  budget and needs a person watching.
- **One `mdw` of `CONFIG0` on unit 3, `GLASSES-125B37`.** Settles the separate and smaller
  question of whether `0xffffffbf` is the shipped value or the donor's history.
  Outstanding since `research/ldrom-2026-08-19.md`. Needs a probe move.
